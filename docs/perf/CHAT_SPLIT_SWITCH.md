# 긴 대화에서의 분할(Ctrl+D·Ctrl+Shift+D)과 탭·프로젝트 전환 성능

2026-11-25 측정과 개선 기록. 재현 도구는 `scripts/perf/chat-heavy.mjs`, 다른 기준선은 [FRAME_COST](FRAME_COST.md).

## 요약

- Ctrl+D는 **좌우 분할**, Ctrl+Shift+D는 **상하 분할**이다(`shortcuts.ts`의 `splitRight`·`splitDown`). 누르면 포커스된 pane 옆에 launcher pane이 생기고 `split-grow`로 자란다.
- 버벅임의 주원인은 **대화 길이가 아니었다.** 짧은 대화(3턴)에서도 같은 구간이 끊겼다. 분할 애니메이션이 매 프레임 채팅 pane의 너비를 바꿀 때, ChatPane이 프레임마다 하던 일(아래 1~3)이 문제였다.
- 대화가 길수록 더 나빠지는 것은 **DOM 크기**였다. 열려 있는 모든 채팅이 대화 전체를 DOM에 들고 있었다(500턴 ≈ 6.7만 요소). 탭·프로젝트를 바꿀 때 보이는 채팅의 스타일·레이아웃 비용과 메모리, 앱을 켤 때의 렌더가 여기에 비례했다.
- 고친 뒤 같은 도구·같은 세션에서 잰 결과: 분할 직후 첫 화면 **72ms → 39ms**, 분할 애니메이션의 끊김(jank) **50ms → 17ms**, 탭 전환 **54ms → 35ms**, 프로젝트 전환 **51ms → 28ms**, 페이지 전체 DOM **14.2만 → 1.6만 요소**.

## 측정 환경과 방법

| 항목 | 값 |
|---|---|
| 코드 | master `a586704` 위의 작업 트리. Vite **개발 빌드**(React dev), 공용 세션 `tmp/main`, 가짜 `claude` |
| 화면 | 3000x1726 창, 120Hz(프레임 간격 8.3ms 단위) |
| 데이터 | 한 프로젝트에 500턴(3,500 이벤트)·3턴 채팅, 다른 프로젝트에 500턴 채팅 하나. 턴 하나 = 사용자 메시지, 도구 2개(Read·Bash), 마크다운·코드·표가 든 답변 |
| 반복 | 조건마다 6회(첫 회 제외) 중앙값 |

```sh
node scripts/verify/session.mjs up --as <이름> && node scripts/verify/session.mjs tab --as <이름>
VERIFY_TAB=<이름> node scripts/perf/chat-heavy.mjs seed     # 채팅 만들기(페이지를 새로고침한 뒤 show 한 번 더)
VERIFY_TAB=<이름> node scripts/perf/chat-heavy.mjs run 6    # JSON 출력
VERIFY_TAB=<이름> node scripts/perf/chat-heavy.mjs clean    # 만든 채팅·탭·프로젝트 정리
```

항목의 뜻:

- `toFirstPaint`: 키 입력 이벤트부터 새 pane이 보인 뒤 두 번째 프레임까지(ms).
- `jank`: 분할 후 0.9초 동안 20ms보다 긴 프레임이 16.7ms를 넘긴 시간의 합(ms). `worst`는 가장 긴 프레임, `over50`은 50ms를 넘은 프레임 수.
- `script`·`style`·`layout`: 같은 동작 0.9초 동안 `Performance.getMetrics`의 증가분(ms).

주의:

- 백그라운드 탭은 `requestAnimationFrame`이 돌지 않는다. 측정 도구가 `Emulation.setFocusEmulationEnabled`로 그 탭만 보이는 것으로 취급한다(창을 앞으로 가져오지 않는다).
- 같은 코드를 연달아 재도 ±30% 흔들린다. 그래서 전·후는 **같은 세션에서 번갈아** 쟀다. 전(前)은 아래 변경을 줄 단위로 끈 상태(윈도잉 끄기 포함)다.
- 개발 빌드라 스크립트 시간의 절대값은 실제 앱(프로덕션 빌드)보다 크다. 상대 비교로만 쓴다. 설치 앱(Electron)에서의 재측정은 하지 않았다.

- `layout`(분할 0.9초 동안의 레이아웃 시간)은 전·후 모두 약 140~170ms로 같다. 분할 애니메이션이 매 프레임 pane 너비를 바꾸는 비용이라 남아 있다. 상하 분할(Ctrl+Shift+D)은 너비가 변하지 않아 약 17ms다. 채팅 본문은 최대 너비(기본 780px)가 있어, 넓은 pane이 그 아래로 줄어들 때부터 줄바꿈이 다시 계산된다.
- 세션 메모리(JS 힙)는 켠 직후 292MB → 179MB, 측정이 끝난 시점 195MB → 126MB다(GC 시점에 따라 흔들리는 값).
- 이력 재생(`fromReplay`, Node에서 4,200 이벤트): 148ms → **53ms**(2,310 이벤트 31ms → 18ms).

## 원인과 변경

| # | 원인 | 변경 | 위치 |
|---|---|---|---|
| 1 | `fit()`(하단 컨트롤 줄이 넘치는지 재는 함수)가 pane 너비가 바뀔 때마다 단계 0부터 4까지 `scrollWidth`를 읽으며 강제 레이아웃을 최대 5번 일으켰다 | 직전에 맞았던 단계에서 시작해 위·아래 한 단계만 확인(보통 1~2번) | `ChatPane.tsx` `fit` |
| 2 | `ResizeObserver`가 pane 너비를 프레임마다 state로 넣어 ChatPane이 매 프레임 다시 그려졌고, 루트의 `--drawer-w`가 매번 바뀌어 대화 전체의 스타일이 다시 계산됐다. 이 값은 서브에이전트 서랍이 열려 있을 때만 쓰인다 | 서랍이 열려 있을 때와 도킹 기준(760px)을 넘을 때만 state를 갱신하고, `--drawer-w`도 서랍이 있을 때만 단다. 서랍이 열리는 순간 실제 너비를 읽는다 | `ChatPane.tsx` `paneWidth` |
| 3 | pane 닫기 유령 애니메이션용 `capture()`가 렌더 때마다(포커스 이동, 제목 변경 포함) 모든 pane의 위치를 읽어 강제 레이아웃을 일으켰다 | 레이아웃·표시·확대 상태가 바뀔 때만 잰다. 700ms 뒤 재측정과 `resize` 갱신은 그대로 | `Panes.tsx` `useCloseGhost` |
| 4 | 열려 있는 모든 채팅이 대화 전체(최대 약 500턴)를 DOM에 들고 있었다 | **윈도잉**: 최근 30턴만 렌더하고, 위로 스크롤해 상단 1,200px 안에 들어오면 30턴씩 더 불러온다. 맨 위에 "이전 대화 N개 더 보기" 버튼이 있다 | `ChatPane.tsx` `turnLimit` |
| 5 | 이력 재생이 도구 결과마다 `results` 객체를 통째로 복사해 이벤트 수의 제곱으로 느려졌다 | 재생 중에만 그 객체를 제자리에서 채우고, 끝나면 복사본을 넘긴다(`replayOwned`) | `chat-model.ts` `fromReplay` |

윈도잉 동작:

- 새 메시지가 오면 가장 아래에 붙고, 따라가기(맨 아래 고정)는 그대로다. 숨겨진 턴 수만 늘어난다(`이전 대화 470개` → `471개`).
- 위로 불러올 때 보던 위치를 지킨다. 브라우저의 스크롤 앵커링은 `scrollTop`이 0일 때(Home 키, 스크롤바를 맨 위로 끌기) 동작하지 않아서, 더하기 전후의 `scrollHeight` 차이만큼 직접 보정한다.
- 열기·맨 아래 따라가기 중에는 더 불러오지 않는다(`stick`). 서버는 이미 최근 4,000 이벤트(약 500턴)만 보내고, 화면 아이템은 최대 2,000개다. 이 한도는 바꾸지 않았다.
- `branch`·`rewind`·재시도·pin(요청 고정줄) 등은 `view.items`를 쓰고 DOM 전체를 가정하지 않아 영향이 없다.

## 확인한 것

- 분할·닫기: 좌우·상하 모두 launcher가 생기고, 닫을 때 유령 애니메이션이 재생된다.
- 긴 채팅을 위로 스크롤하면 30턴씩 늘고(30→60→…→270→…), 새 메시지를 보내면 맨 아래에 붙고 숨김 수가 1 늘며 렌더는 30턴을 유지한다.
- `pnpm typecheck` 통과. `node --test` 1,031개 중 실패 2개는 이번 변경과 무관하다(`runShell` macOS `/private` 경로, git trailer 훅 테스트). 새 테스트 `fromReplay fills results in place…`(`tests/chat-model.test.mjs`)가 재생 결과가 이벤트별 `reduce`와 같고 반환된 맵을 다른 곳이 바꾸지 않음을 확인한다.

## 남은 것

- 분할 애니메이션 자체의 레이아웃(약 140ms/0.9초)은 그대로다. 줄이려면 애니메이션을 `transform`으로 바꾸거나 자라는 동안 기존 pane의 너비를 고정해야 하며, 모양이 바뀌는 일이라 하지 않았다.
- 보이지 않는 탭의 채팅도 마운트된 채로 둔다(30턴만). 탭 수가 많을 때의 `ChatPane` 재렌더는 `PaneContent` memo가 `chat` 컨텍스트 객체가 매번 새로 만들어져 깨져 있는데, 지금 측정에서는 비용이 작아(전체 약 6ms) 건드리지 않았다.
- 서버가 보내는 이력(최근 4,000 이벤트)을 더 줄이면 켤 때와 재연결 때 더 빨라진다. 위로 스크롤할 때 서버에서 더 가져오는 방식이 필요해 이번 범위 밖이다.
- 위 수치는 합성 대화다. 실제 대화는 큰 이미지, 긴 diff, mermaid가 더 있어 DOM 비용이 더 클 수 있다(윈도잉의 이득도 더 크다).
