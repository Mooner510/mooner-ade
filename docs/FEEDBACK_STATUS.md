# 피드백 처리 상태 추적 (대기 · beta 반영 · 릴리스 반영)

피드백 요청으로 제출한 건마다 "지금 어디까지 왔는지"를 앱 안에서 보여 주기 위한 설계와, 앱이 Hub에 기대하는 응답 계약입니다.
앱 쪽은 구현되어 있고, **Hub 쪽(엔드포인트·라벨 규약)은 아직 없습니다.** Hub가 준비되기 전에는 건마다 기존의 "제출됨"만 보이고 아무것도 깨지지 않습니다.

## 1. 앱이 보여 주는 것

| 상태 | 뜻 | 배지 |
|---|---|---|
| `pending` | 이슈가 열려 있고 아직 반영 전 | 대기 |
| `beta` | beta 버전에 반영됨 | beta 반영 v0.6.0-beta5 |
| `released` | 정식 릴리스에 반영됨 | 릴리스 반영 v0.6.0 |
| `closed` | 닫혔지만 반영 버전을 알 수 없음(옛 이슈) | 처리됨 |
| `declined` | 반영하지 않기로 하고 닫힘 | 반영하지 않음 |

- 배지는 피드백 내역의 각 줄과 상세 화면에 보입니다. Hub가 아직 아무 말도 하지 않은 건은 "제출됨"으로 남습니다.
- **현재 앱 버전과의 비교**: 반영 버전이 있으면 "지금 쓰는 버전에 이미 반영되어 있습니다 / 아직 없습니다 (v… 이상으로 업데이트)"를 보여 줍니다(`0.6.0-beta5 < 0.6.0 < 0.6.1-beta1`, beta 번호는 숫자로 비교).
- **beta → 릴리스 자동 승격**: beta 버전에 반영된 건은, 그 버전 이상의 정식 릴리스가 생기면(Hub가 준 `latestStable`, 또는 이 앱 자신이 정식 버전이고 그 이상일 때) 이슈를 다시 고치지 않아도 `released`로 보입니다.
- **알림**: 처리 상태가 바뀌면 앱 안 토스트로 한 번 알립니다(여러 건이면 "N건의 처리 상태가 바뀌었어요"). 앱이 꺼져 있던 동안 바뀐 것은 다음 실행 때 한 번 알립니다. 건을 열어 보면 "읽음"이 되어 점이 사라지고 다시 알리지 않습니다. 같은 건이 beta → 릴리스로 또 바뀌면 새 소식입니다. 처음 확인한 `pending`은 소식이 아닙니다.
- **조용히 후퇴**: Hub가 404/405/501로 답하거나, 네트워크가 안 되거나, 계정 제출인데 로그인한 플러그인이 조회를 못 하면 오류 표시 없이 "제출됨"으로 둡니다. 엔드포인트가 없다고 판단하면 하루 동안 묻지 않습니다("지금 확인"을 누르면 바로 다시 묻습니다).

## 2. 앱이 Hub에 묻는 방식

- 앱 서버(`apps/local-server/src/feedback-progress.js`)가 **앱이 켜져 있는 동안 15분마다**(켠 뒤 20초 첫 확인) 묻습니다. 대상은 제출됨 중 아직 `released`/`declined`가 아닌 건뿐이고, 한 번에 50건씩 묶어 한 번의 요청으로 보냅니다.
- 실패하면 15분 × 2ⁿ(최대 6시간)으로 늦추고, `Retry-After`가 있으면 그만큼은 기다립니다. 오류를 사용자에게 띄우지 않습니다.
- 앱은 **키(피드백 id)만 보내고, 건당 `{state, version}`만 받습니다.** 제목·본문·이미지를 다시 내려받지 않습니다.
- 개발·시험용: `ADE_FEEDBACK_STATUS=0`이면 끕니다. `ADE_FEEDBACK_STATUS_MS`(주기), `ADE_FEEDBACK_STATUS_FIRST_MS`(첫 확인)로 시험 때 줄일 수 있습니다.

## 3. Hub 계약 (Hub가 만들어야 하는 것)

### 3.1 엔드포인트

```
GET /v1/feedback/status?keys=<clientKey>,<clientKey>,...
```

- `keys`: 1~50개, 각 `[A-Za-z0-9_-]{8,64}`. 앱이 제출 때 보낸 `clientKey`(= 앱의 피드백 id)입니다.
- **인증은 제출과 같은 두 가지**이고, **자기가 보낸 건만** 조회됩니다. Hub가 이미 저장하는 `feedback` 행((계정 또는 익명 기기 해시, `client_key`) → `issue_number`)으로 찾으면 됩니다.
  - 로그인: `Authorization: Bearer <access>`(원격 접속 플러그인이 `POST /v1/feedback`에 쓰는 토큰). 그 계정의 행만.
  - 익명: 헤더 `X-ADE-Device`(제출 때와 같은 설치 id). 그 기기 해시의 행만.
- 다른 사람의 키, 모르는 키는 응답의 `items`에 **그냥 빠집니다**(404가 아님. 키 존재 여부를 알려 주지 않기 위해서).

응답 `200`:

```json
{
  "items": {
    "lq3k9x2a-1f2e3d4c5b6a": { "state": "beta", "version": "0.6.0-beta5", "issueNumber": 18 },
    "lq3k9x2b-aa11bb22cc33": { "state": "pending", "issueNumber": 22 }
  },
  "latestStable": "0.6.0",
  "checkedAt": "2026-11-20T09:00:00Z"
}
```

- `state`: `pending | beta | released | closed | declined` (모르는 값은 앱이 무시합니다).
- `version`: 반영 버전(`0.6.0-beta5`, 앞의 `v`는 있어도 됨). 없으면 생략.
- `latestStable`(선택): 가장 최근 정식 릴리스 버전. 있으면 beta 반영 건을 자동으로 "릴리스 반영"으로 올립니다.
- 본문·제목·댓글 내용은 **절대 넣지 않습니다.**

오류: `400 bad_request`(키 형식·50개 초과), `401 unauthorized`(로그인 토큰), `429 rate_limited`(+`Retry-After`), `502 upstream_failed`(GitHub), `503 feedback_disabled`. 앱은 모두 조용히 넘기고 다음 주기에 다시 묻습니다. 이 엔드포인트가 없는 Hub(404/405/501)는 "아직 지원 안 함"으로 보고 하루 쉽니다.

권장: 기기·계정당 분당 6회 정도로 제한하고, GitHub 이슈 조회는 이슈별 60초 캐시(또는 ETag 조건부 요청)로 GitHub rate limit을 보호합니다. Hub의 피드백용 토큰은 이미 Issues 읽기·쓰기 권한이 있어 **새 GitHub 권한은 필요 없습니다**(댓글 읽기도 Issues 권한).

### 3.2 상태 판정 규칙 (Hub가 이슈에서 계산)

라벨을 기준으로 하고, 라벨이 없는 옛 이슈는 닫힘+댓글로 보완합니다. 댓글 파싱만으로는 형식이 흔들릴 때 깨지고(작성자 필터, 수정·삭제, 댓글 API 한 번 더), 라벨은 한 번의 이슈 조회로 읽히고 고치기 쉬워 이쪽을 정식 규약으로 권합니다.

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | 라벨 `fixed-in:<버전>`이 있음 (예: `fixed-in:0.6.0-beta5`) | 버전에 `-`(프리릴리스)가 있으면 `beta`, 없으면 `released`. 이슈가 열려 있어도 라벨이 우선 |
| 2 | 닫힘 + (`wontfix` 라벨 또는 `state_reason: not_planned`) | `declined` |
| 3 | 닫힘 + 라벨 없음 + 저장소 소유자(또는 메인테이너)의 댓글에 `<버전>에서 반영` | 그 버전으로 1번과 같은 판정 (**지금까지 닫은 이슈와 호환**: 댓글 형식 `0.6.0-beta5에서 반영`) |
| 4 | 닫힘 + 위 어느 것도 없음 | `closed` |
| 5 | 열림 + `fixed-in` 없음 | `pending` |

- 여러 `fixed-in` 라벨이나 댓글이 있으면 가장 높은 버전을 씁니다.
- 새 이슈는 반영할 때 `gh issue edit <번호> --add-label fixed-in:<버전>` 한 줄이면 됩니다. 정식 릴리스가 나온 뒤에는 beta 건을 다시 고칠 필요가 없습니다(앞의 자동 승격). 옛 이슈를 라벨로 옮기는 일은 선택입니다(댓글 보완이 있으므로 급하지 않음).
- 라벨은 피드백 저장소에 미리 만들어 둘 필요가 없지만(GitHub가 첫 사용 때 만듭니다), 색·설명을 맞추려면 `fixed-in:*`를 한 번 만들어 두세요.

### 3.3 계정으로 제출한 건 (플러그인 경유)

계정 제출은 앱이 직접 Hub에 인증할 수 없어 원격 접속 플러그인이 대신 보냅니다. 조회도 같은 길입니다([PLUGINS.md](PLUGINS.md)의 피드백 절).

- 플러그인이 `feedback` 메시지에 `statusQuery: true`를 보내면 "조회할 수 있다"는 뜻입니다. 그렇지 않은 플러그인에는 묻지 않고, 그 계정 건은 "제출됨"으로 남습니다.
- 앱 → 플러그인: `{type:'feedback/status', id, keys:[…]}`. 플러그인은 위 엔드포인트를 계정 토큰으로 호출해 `{type:'feedback/status-result', id, ok:true, items, latestStable?}` 또는 `{ok:false, error:{code, retryAfter?}}`로 답합니다. 앱은 `items`의 모양(키 형식, `state` 값, 버전 형식)을 다시 검사하고 나머지는 버립니다. 40초 안에 답이 없으면 실패로 칩니다.

## 4. 앱 쪽 저장

제출된 건의 `feedback.json`에 `track`을 **더하기만** 합니다(옛 파일은 그대로 읽히고, `track`이 없으면 "아직 확인 안 함"). 건의 상태(`submitted`)·`updatedAt`·본문은 바뀌지 않습니다.

```
track: { state, version?, sig, seenSig?, checkedAt, changedAt, latestStable? }
```

`sig = "state:version"`, `seenSig`는 사용자가 본 `sig`입니다. `sig !== seenSig`이고 `pending`이 아니면 새 소식입니다. 표시용 `progress`(`news`, 현재 앱 버전 기준 `inApp` 포함)는 목록을 읽을 때마다 계산하며 저장하지 않습니다. 기록은 지우거나 줄이지 않습니다.

## 5. Hub 담당이 해야 할 일 요약

1. `GET /v1/feedback/status` 구현(위 3.1, 두 가지 인증, 자기 건만, 본문 없는 응답, rate limit·캐시).
2. 상태 판정(3.2): `fixed-in:<버전>` 라벨 + 옛 이슈용 댓글 보완(`<버전>에서 반영`).
3. (선택) `latestStable`: ADE 저장소의 가장 최근 정식 릴리스 태그.
4. 원격 접속 플러그인(비공개 저장소): `feedback` 메시지에 `statusQuery: true`, `feedback/status` 처리(계정 토큰으로 3.1 호출 후 `feedback/status-result`).
5. 이슈를 반영할 때마다 `fixed-in:<버전>` 라벨 달기(운영 습관).
